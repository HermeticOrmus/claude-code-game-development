## Code of Conduct

This project adheres to a Code of Conduct that all contributors are expected to follow. Please read [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) before contributing.

**In summary**: Be respectful, inclusive, and constructive in all interactions.

## How Can I Contribute?

There are many ways to contribute to this project:

### 1. Add New Game Examples

We're always looking for new game examples that demonstrate different concepts or genres.

**What we're looking for**:
- Complete, working games with source code
- Detailed README explaining architecture and concepts
- PROMPTS.md documenting the Claude Code workflow
- Well-commented code with explanations
- Examples that fill gaps in our current collection

**Current priorities**:
- Racing games
- Fighting games
- Rhythm/music games
- Strategy games (turn-based, 4X)
- Simulation games
- VR/AR examples
- Mobile-specific examples

### 2. Improve Documentation

Documentation improvements are always welcome:

- Fix typos, grammar, or technical errors
- Add code examples to existing documentation
- Clarify complex explanations
- Translate documentation to other languages
- Add diagrams or visual aids
- Expand sections that need more detail

### 3. Contribute Prompts

Share prompt engineering discoveries:

- New prompt patterns that work well for game development
- Refinements to existing prompts
- Domain-specific prompts (VR, mobile, multiplayer)
- Meta-prompts for prompt generation
- Troubleshooting prompts for common issues

### 4. Create Templates

New project templates help developers start faster:

- Framework-specific templates (Unity WebGL, Godot HTML5, etc.)
- Genre-specific templates (RPG starter, FPS starter, etc.)
- Architecture templates (ECS, MVC, etc.)
- Deployment templates (Docker, CI/CD configurations)

### 5. Build Tools and Utilities

Helper tools enhance the development experience:

- Code analysis tools
- Asset optimization scripts
- Performance profiling utilities
- Testing frameworks
- Build automation
- Development servers

### 6. Report Issues

Found a bug or have a suggestion?

- Check if the issue already exists
- Provide detailed reproduction steps
- Include your environment (OS, browser, Node version)
- Add screenshots or code snippets if helpful
- Suggest potential solutions if you have ideas

## Getting Started

### Prerequisites

Before contributing, ensure you have:

- Git installed and configured
- Node.js (v16 or higher)
- A code editor (VS Code recommended)
- Claude Code installed (for testing prompts)
- Basic knowledge of JavaScript/TypeScript
- Familiarity with game development concepts

### Setting Up Your Development Environment

1. **Fork the repository** on GitHub

2. **Clone your fork**:
   ```bash
   git clone https://github.com/YOUR_USERNAME/claude-code-game-development.git
   cd claude-code-game-development
   ```

3. **Add upstream remote**:
   ```bash
   git remote add upstream https://github.com/ORIGINAL_OWNER/claude-code-game-development.git
   ```

4. **Install dependencies** (if adding tools that require them):
   ```bash
   npm install
   ```

5. **Create a feature branch**:
   ```bash
   git checkout -b feature/your-feature-name
   ```

## Contribution Guidelines

### Game Examples

All game examples must meet these requirements:

#### Functionality
- Game must be complete and playable
- No critical bugs or crashes
- Runs at stable frame rate (60 FPS on modern hardware)
- Works in latest versions of Chrome, Firefox, and Edge
- Mobile-responsive (if applicable)

#### Code Quality
- Follow JavaScript/TypeScript best practices
- Use ES6+ features appropriately
- Include comprehensive comments explaining complex logic
- Note where code was generated by Claude Code
- Handle errors gracefully
- No console errors or warnings
- Follow security best practices (no XSS, injection vulnerabilities)

#### Documentation
- README.md with:
  - Game description and learning objectives
  - Architecture explanation
  - How to run the game
  - Key concepts demonstrated
  - Extension ideas
- PROMPTS.md with:
  - Chronological development log
  - Exact prompts used
  - Results analysis
  - Refinements made
  - Lessons learned

#### File Structure
```
game-name/
├── README.md (1500+ words)
├── PROMPTS.md (500+ words)
├── index.html
├── game.js (or src/ directory for complex games)
├── style.css
├── assets/ (if needed)
└── package.json (if using build tools)
```

#### Code Comments Style

Use this commenting style:

```javascript
// ✅ GOOD: Explains why, notes AI assistance
// Use object pooling to prevent garbage collection spikes during gameplay
// Generated with Claude Code prompt: "Create a reusable object pool for particles"
// Modified to add automatic pool expansion when capacity is exceeded
class ObjectPool {
  constructor(factory, initialSize = 100) {
    this.factory = factory;
    this.pool = [];
    this.active = [];

    // Pre-allocate pool
    for (let i = 0; i < initialSize; i++) {
      this.pool.push(factory());
    }
  }

  acquire() {
    // Return from pool or create new if empty
    if (this.pool.length === 0) {
      return this.factory();
    }
    const obj = this.pool.pop();
    this.active.push(obj);
    return obj;
  }

  release(obj) {
    const index = this.active.indexOf(obj);
    if (index !== -1) {
      this.active.splice(index, 1);
      this.pool.push(obj);
    }
  }
}

// ❌ BAD: States the obvious, no context
// This is a class
class ObjectPool {
  // Constructor
  constructor(factory, initialSize = 100) {
    // Set factory
    this.factory = factory;
    // Create pool array
    this.pool = [];
  }
}
```

### Documentation

Documentation contributions must meet these standards:

#### Technical Accuracy
- All code examples must work correctly
- Technical explanations must be accurate
- Links must be valid and current
- Version-specific information must be noted

#### Writing Style
- Clear, concise, beginner-friendly language
- Active voice preferred
- Short paragraphs (3-4 sentences)
- Use headings for scanability
- Include concrete examples
- Avoid jargon (or explain when necessary)

#### Structure
- Start with learning objectives
- Include prerequisites
- Provide table of contents for long documents
- End with "next steps" or related topics
- Cross-reference related documents

#### Code Examples
- All code examples must be complete and runnable
- Include setup/context needed to run the code
- Explain what the code does
- Show Claude Code prompts used (where applicable)
- Note any modifications to AI-generated code

## Style Guidelines

### JavaScript/TypeScript

We follow standard JavaScript best practices with these specifics:

```javascript
// Use const by default, let when reassignment needed
const config = { /* ... */ };
let score = 0;

// Use meaningful variable names
const playerVelocity = { x: 0, y: 0 };  // Good
const pv = { x: 0, y: 0 };              // Bad

// Use arrow functions for callbacks
enemies.forEach(enemy => enemy.update(deltaTime));

// Use template literals for strings
console.log(`Score: ${score}`);  // Good
console.log("Score: " + score);  // Avoid

// Use destructuring
const { x, y } = player.position;  // Good
const x = player.position.x;       // Works, but destructuring preferred

// Use async/await over promises when possible
async function loadAssets() {
  const sprites = await fetch('/sprites.json');
  return sprites.json();
}

// Comment complex logic
// Calculate trajectory using ballistic motion equations
// v = v0 + at, where v0 is initial velocity, a is acceleration, t is time
const velocity = initialVelocity + (acceleration * deltaTime);
```

### File Naming

- Use kebab-case for files: `player-controller.js`, `game-state-manager.js`
- Use PascalCase for class files: `PlayerController.js`, `EnemyAI.js`
- Use descriptive names: `collision-detection.md` not `cd.md`

### Git Commit Messages

Follow conventional commits format:

```
Type: Short description (max 50 chars)

Longer description if needed (wrap at 72 chars)

Types:
- Add: New feature or file
- Fix: Bug fix
- Docs: Documentation changes
- Refactor: Code refactoring without behavior change
- Test: Adding or updating tests
- Chore: Maintenance tasks
```

Examples:
```
Add: Snake game example with grid-based movement

Implements classic Snake game demonstrating:
- Grid-based movement system
- Array-based snake body management
- Collision detection with self and walls
- Score persistence with localStorage
```

```
Fix: Collision detection in Pong game

Ball was passing through paddles at high velocities.
Implemented continuous collision detection to prevent tunneling.
```

```
Docs: Expand pathfinding algorithms section

Added A* implementation examples and performance comparison
with Dijkstra. Includes benchmarks for different grid sizes.
```

## Pull Request Process

### Before Submitting

1. **Test thoroughly**:
   - All games work without errors
   - All code examples run correctly
   - Links are valid
   - No console errors/warnings

2. **Update documentation**:
   - Update README if adding new sections
   - Add entries to relevant documentation indices
   - Update learning paths if applicable

3. **Follow style guidelines**:
   - Run linter (if configured)
   - Format code consistently
   - Use proper commit message format

4. **Keep scope focused**:
   - One feature/fix per pull request
   - Don't mix unrelated changes
   - Keep pull requests reasonably sized

### Submitting Pull Request

1. **Push to your fork**:
   ```bash
   git push origin feature/your-feature-name
   ```

2. **Create pull request on GitHub**:
   - Use descriptive title
   - Fill out the pull request template
   - Link related issues
   - Add screenshots/GIFs for visual changes

3. **Pull request template**:
   ```markdown
   ## Description
   [Clear description of what this PR does]

   ## Type of Change
   - [ ] New game example
   - [ ] Documentation improvement
   - [ ] Prompt contribution
   - [ ] Bug fix
   - [ ] New feature
   - [ ] Other: [describe]

   ## Testing
   [How you tested these changes]

   ## Checklist
   - [ ] Code follows style guidelines
   - [ ] All examples work correctly
   - [ ] Documentation updated
   - [ ] Commit messages follow convention
   - [ ] No console errors/warnings
   - [ ] Tested in multiple browsers (if applicable)

   ## Screenshots
   [If applicable]

   ## Related Issues
   Fixes #[issue number]
   ```

### Review Process

1. **Automated checks**: Must pass (if configured)
2. **Maintainer review**: May request changes
3. **Discussion**: Be responsive to feedback
4. **Approval**: Requires approval from maintainer
5. **Merge**: Maintainer will merge when ready

### After Merge

- Your contribution will be included in the next release
- You'll be added to the contributors list
- Consider sharing your contribution on social media!
